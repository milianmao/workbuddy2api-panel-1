# 会话粘性与缓存槽

多轮对话尽量落到同一账号（前缀缓存命中、避免每轮换号），同时不牺牲可用性：绑定号失效立即解绑重分配。

## 触发点

- 每个聊天请求解析会话键：`session.ExtractKey(body)`（`internal/session/session.go:335`）。提取顺序 `metadata.conversation_id` → `metadata.conversationId` → 顶层 `conversation_id` → `conversationId` → `prompt_cache_key`；带 `user_id` 时**不派生**。
- 粘性开关：`session_sticky.enabled`（默认 true）。关闭时绑定逻辑不生效，但会话头族仍按会话级聚合（提取与粘性解耦，`handler.go:856-860`）。
- 前置条件：解析出非空 `sessKey`；否则走纯轮换。

## 数据流路径

请求 body → `ExtractKey` 得 `sessKey` → `Router.ResolveForModel(sessKey, routeModel)` → 命中且该账号在**当前模型**上可用（`AvailableForModel` 过滤）→ 命中且 TTL 未过期 → `touch` 滚动续期 → 返回 uid → handler 用 `PickByUIDForModel(uid, curModel)` 复核（在途未满、`healthyForModel`、积分保底）→ 通过则直接用 → 失败/被抢 → `Unbind` 并从 Redis 删镜像 → 回落普通轮换 → 成功号 `Bind(sessKey, uid)` 覆盖旧绑定。

未命中 → 慢路径：写锁 re-check → 若仍无则双段分配（优先"当前空闲号"，否则全池）→ 绑定。

## 为什么派生键只用于缓存槽

只发 `user_id` 的客户端若按 user 维度派生粘性，同账号上多段对话会互相覆盖前缀缓存（issue #5：`glm-5.3` 大上下文周期性命中率掉到 0.2%）。因此：

- 派生键 `cacheKeyID` **只**喂给上游的 `prompt_cache_key` 槽位；
- 账号绑定仍只认 `sessKey`，不复活 user 维度粘性（`handler.go:856-866` 注释）。

## 异常处理

- 绑定号冷却/占满：`ResolveForModel` 视为失效 → 慢路径重分配（`session.go:154-160`）。
- 绑定号被本次 `Acquire` 抢输（并发）：立即 `Unbind` + 换号，避免下一轮仍撞同一满载粘性号再浪费一次往返（`handler.go:1112-1117`）。
- 绑定号积分触底 + 收费模型：返回 nil 并解绑，粘性号回血后下次会话重新绑定（`internal/pool/state.go:517-525`）。
- 绑定号在某模型被 6004 限额：按模型判可用 → 重新分配，不钉在限额号上反复失败。
- TTL 过期：快路径判定 `expired` → 慢路径重分配；GC 同时清理并删 Redis 镜像。
- Redis 不可用：`LoadFromStore` 拿不到数据 → 本地空表；写镜像失败静默，进程内绑定仍有效。
- 客户端中途换会话键：下一请求即按新键分配（旧绑定靠 TTL/GC 回收）。
- 粘性关闭：不绑定不解析，所有请求按加权轮换。
