# 用量与扣费记账

四条独立账本，刻意不合并——它们的驱动方式、精度和保留策略完全不同。

## 触发点

- **逐请求用量**（`internal/usage`）：每次聊天/图像尝试结束即 `usage.Add`（`internal/server/handler.go:960-965`、`internal/server/images.go:236`）。事件驱动：没有请求就没有数据点。
- **余额趋势**（`internal/balance`）：余额刷新路径顺手 `Balance.Add`（`internal/scheduler/scheduler.go:921-926`）。定时驱动：每 30min 每账号一点。
- **积分变动流水**（`internal/credithist`）：`upstream.Client.creditObserver` 在**每次真实查到余额**后回调（`internal/upstream/client.go:2732-2754`），装配在 `cmd/server/main.go:347-349`。变动驱动。
- **请求归档**（`internal/reqlog`）：`ServeHTTP` 入口为 POST 聊天四路径建 trace，请求结束 `Record`（`internal/server/handler.go:239-259`）。每请求一条。
- **日/突发预算**（`internal/server/budget.go`）：`admit()` 在请求入口，`st.done()` 在请求出口累加（`internal/server/logging.go:114-116`）。

## 数据流路径

请求结束 → `recordAttempt(...)` → `validUsageCost` 闸门（有回执才信）→ `Pool.RecordTokenUsage`（每账号累计计数器）+ `Usage.Add`（按桶累计）→ `st.done()` → `budget.add(observed credit)` + `observeCache` + `noteProm` → `reqlog.Record(event)` → JSONL 归档队列。

余额查询 → 上游返回 credits/批次 → `p.SetCreditsSnapshot` / `SetCreditsDetailed` → `creditObserver(uid, credits)` → `credithist.Observe`（与上次比对，变动即留痕、同步原子写盘）→ `balance.Add`（按账号 30min 节流采样）→ 面板三视图读取。

## 四本账的分工

| 账本 | 键 | 记录什么 | 保留 | 位置 |
|---|---|---|---|---|
| usage | `scope\|realm\|uid\|model\|rate`，`scope="h:"+2006-01-02T15`（本地时区） | 请求数、错误数、token 数、缓存命中、延迟、TPS、credit | 小时桶 90 天，更早折叠为日桶**永久保留**；硬上限 40 万桶 | `data/usage.json` |
| balance | uid | 余额采样点（另含每日折叠点） | 原始点 30 天；更早按 (uid, 本地日) 折叠；总量上限 20 万点 | `data/balance_history.json` |
| credithist | 流水条目 | 每次余额变动的 delta | 2000 条（丢最旧） | `data/credit-history.json` |
| reqlog | 事件 | 模型、耗时、状态、outcome、来源（可选） | 7 天 + 总容量 100 MiB 双限；内存最近 100 条 | `data/request-logs/requests-YYYY-MM-DD.jsonl` |

**为什么不合并**：`internal/usage` 与 `internal/balance` 的包注释明确写了——usage 是事件驱动（流量），balance 是定时驱动（存量）；没有请求就查不到余额，两者无法互相推导（`internal/balance/balance.go:1-10`、`internal/usage/usage.go:1-10`）。

## 关键节点详解

| 节点 | 文件位置 | 核心逻辑 | 异常处理 |
|---|---|---|---|
| usage 桶键 | `internal/usage/usage.go:189-193`、`:44-47` | 空 realm→`cn`，空 model→`(unknown)`；rate 维度让同模型不同倍率分开统计 | 无 |
| usage 保留 | `usage.go:34-42`、`:244-316` | `hourlyKeep=90d`；超 `maxBuckets=400000` 强制从最旧小时桶折叠 | 折叠不丢总量 |
| usage 落盘 | `usage.go:319-368` | 30s 防抖 flush + `safefile.WriteKeep`；`fileVersion=4` | 坏文件回退 `.bak` |
| balance 节流 | `internal/balance/balance.go:31`、`:160-181` | `sampleInterval=30min`，**按账号**记 `lastSample`（全局时间戳会让多号只剩一条线） | 未到间隔直接返回 false |
| balance 两级粒度 | `balance.go:35-52`、`:193-285` | 30 天内原始点；更早按日折叠并保留当日 `Consumed/Gained/First`（否则历史日消耗恒 0）；365 天后丢弃 | 超 20 万点触发折叠 |
| credithist 规则 | `internal/credithist/credithist.go:116-160` | 首次只建基线；同值返回；`\|delta\| <= 1_000_000` 才追加（超限视为上游脏数据/哨兵，只更新基线） | 落盘失败只记日志，不影响主流程 |
| 回执闸门 | `internal/server/handler.go:1819-1843` | `validUsageCredit` / `validUsageCost`：只有上游给了合法 usage 才记账 | 无回执只记请求数不记扣费 |
| 预算只统计已观测 | `internal/server/budget.go:110-124` | `add(observed)` 不估算；日切 CST 惰性归零（`:184-196`） | 估算漂移会误拦，宁可少拦 |
| reqlog 背压 | `internal/reqlog/reqlog.go:298-307` | 队列满即丢并 `dropped.Add(1)`，绝不阻塞模型请求 | 错误暴露在 `ArchiveStats.LastError` |
| reqlog 脱敏 | `reqlog.go:1-6`、`:58-63`；`internal/server/logging.go:452-472` | 不写提示词/响应正文/Authorization；账号只存 `昵称(uid8)`；UA 截断 200 字节 | 来源受 `request_client_info` 开关控制 |

## 异常处理

- 上游 usage 缺失或非法（负数、NaN、超范围）：不记账，仅计请求数。防"脏 usage 把日预算打穿"。
- 取消/中断的请求：记 `outcome=interrupted`，不计入失败率统计（断连是结果不是失败）。
- usage 文件损坏：`safefile.Read` 回退 `.bak`；仍坏则按空账本启动（不阻塞服务）。
- 余额查询 401：不写负值，走 401 求证链路（见 [定时任务与保号](定时任务与保号.md)）。
- 积分变动超过 100 万：判为上游脏数据/哨兵值，只更新基线不留流水。
- 归档队列满：丢弃 + 计数，面板「运行日志」可见 `dropped_writes`。
- 日预算跨日：`admit()` 里惰性判断 `day != 今天` 则归零；重启也按 CST 日重新计。
- 缓存命中率低闸：连续 5 轮低于 `budget.cache_low_rate` → 冷却 60s（`budget.go:75-110`）。
